[JUnit 글](/blog/junit-testing/)과 [Postman→JUnit 글](/blog/postman-to-junit/)에서 테스트를 **어떻게 쓰는지**를 봤다. 그런데 막상 공부하다 보면 용어가 우수수 쏟아진다 — 단위·통합·시스템·인수·E2E, 블랙박스·화이트박스, 컨트롤러·서비스·리포지토리 테스트. *"이걸 다 JUnit으로 하나?"* 싶다. 이번엔 이 뒤섞인 것들을 **하나의 지도**로 정리하며 테스트 주제를 마무리한다.

## 먼저 — JUnit은 "종류"가 아니다

가장 큰 오해부터 풀자. **JUnit은 테스트의 한 종류가 아니라, 테스트를 돌리는 실행 도구(엔진)**다. 위 용어들은 "무엇을·어떤 관점으로 보나"의 분류이고, JUnit은 "그걸 뭘로 실행하나"다. **층위가 다르다.** 그래서 하나의 축에 나란히 놓으면 헷갈린다.

용어들은 사실 **세 개의 서로 다른 축**으로 나뉜다.

## 축 1) 범위 — 테스트 피라미드

**얼마나 넓게 보느냐**의 축이다.

```
        /\      E2E        ← 적게 (느림·비쌈, 사용자 시나리오 전체)
       /  \     통합        ← 중간 (여러 컴포넌트 연동)
      /____\    단위        ← 많이 (빠름·쌈, 메서드 하나)
```

| 범위 | 보는 것 |
|---|---|
| **단위(Unit)** | 메서드·클래스 하나만 격리 (Mock으로 의존 끊음) |
| **통합(Integration)** | 여러 개 연동 (서비스+리포지토리+DB) |
| **시스템(System)** | 배포된 전체 시스템 |
| **E2E** | 사용자 관점, 처음부터 끝까지 |
| **인수(Acceptance)** | "요구사항을 충족하나" (비즈니스·고객 관점) |

아래가 넓고(단위 많이), 위가 좁다(E2E 적게). 단위는 싸고 빠르니 많이, E2E는 비싸니 핵심만 — 이게 **테스트 피라미드**다.

## 축 2) 관점 — 블랙박스 vs 화이트박스

**내부를 아느냐**의 축이다. 범위 축과는 완전히 다른 자다.

| | 내부 구현 | 보는 것 |
|---|---|---|
| **블랙박스** | 모름 | 입력 → 출력만 ("기능이 맞나") |
| **화이트박스** | 앎 | 내부 분기·경로까지 (커버리지) |

단위 테스트를 화이트박스로 할 수도, 블랙박스로 할 수도 있다. **축이 다르니 서로 겹쳐서 조합**된다.

## 축 3) 스프링 계층 — 범위 축의 실무 버전

컨트롤러·서비스·리포지토리 테스트는 사실 **범위 축을 스프링 구조에 맞춘 것**이다.

| 계층 테스트 | 보통 이 범위 | 스프링 도구 |
|---|---|---|
| **컨트롤러** | 슬라이스/단위 | `@WebMvcTest` + MockMvc |
| **서비스** | 단위 (Mockito) | `@ExtendWith(MockitoExtension)` |
| **리포지토리** | 통합 (DB) | `@DataJpaTest` |

## E2E의 두 얼굴 — API E2E vs UI E2E

여기가 가장 헷갈리는 지점이다. "E2E"의 **"End(끝)"가 어디냐**가 관점마다 다르다.

```
[사용자] 버튼 클릭
   │
   ▼
[프론트엔드]  ── HTTP ──▶  [백엔드: 컨트롤러→서비스→리포지토리→DB] → 응답
   │                        └──────── API E2E 범위 ────────┘  (UI 없음)
   ▼
[화면에 결과 표시]
   └────────────────── UI E2E (진짜 E2E) 범위 ──────────────────┘  (버튼부터)
```

- **API E2E** — **백엔드의** 끝에서 끝(HTTP 진입 → DB → 응답). 진짜 DB·전 계층을 통과하지만 **UI(버튼)는 없다.** 코드로 HTTP 요청을 직접 쏜다
- **UI E2E** — **사용자의** 끝에서 끝. 브라우저에서 **버튼 클릭부터** 화면 결과까지 전부

*"이게 무슨 end-to-end야, 버튼도 안 누르는데"* 싶은 위화감이 정확하다. 버튼 클릭은 **UI E2E**의 몫이다.

## 그래서 — 뭘 뭘로 하나 (도구 지도)

```
JUnit으로 (엔진):
  ✓ 단위 · 통합 테스트
  ✓ 컨트롤러(@WebMvcTest) · 서비스(Mockito) · 리포지토리(@DataJpaTest)
  ✓ API E2E (RestAssured · TestRestTemplate)

JUnit 밖 (다른 도구):
  ✗ UI E2E      → Selenium · Cypress · Playwright (브라우저 자동화)
  ✗ 인수 테스트  → Cucumber (BDD) 또는 수동
  ✗ 성능·부하    → JMeter · Gatling
```

대부분은 JUnit(+스프링 테스트+Mockito) 위에서 쓰고, **UI E2E만 별도 도구**를 쓴다.

## 테스트는 언어를 가리지 않는다

이 지도는 자바·스프링만의 것이 아니다. **프론트엔드(React)에도 그대로** 있다.

| 백엔드(Java) | 프론트(React) |
|---|---|
| JUnit (실행기) | **Jest / Vitest** |
| AssertJ (단언) | `expect(...)` |
| Mockito (모킹) | `jest.mock(...)` |
| `@WebMvcTest` (슬라이스) | **React Testing Library** |
| Selenium (UI E2E) | Cypress · Playwright |

구조도 똑같다. given-when-then(≡ AAA: Arrange-Act-Assert)이 프론트에도 있다.

```jsx
test('증가 버튼을 누르면 카운트가 오른다', () => {
  render(<Counter />);                              // given
  fireEvent.click(screen.getByText('증가'));         // when
  expect(screen.getByText('1')).toBeInTheDocument(); // then
});
```

**언어·프레임워크만 다르지, 테스트의 철학은 하나**다 — 준비하고, 행동하고, 검증한다.

## 한 장으로 정리

```
"얼마나 넓게 보나"  → 단위 · 통합 · 시스템 · E2E   (범위 축 = 피라미드)
"내부를 아나"       → 블랙박스 · 화이트박스        (관점 축)
"어느 계층을 보나"   → 컨트롤러 · 서비스 · 리포지토리 (스프링 계층 = 범위의 실무형)
"뭘로 돌리나"       → JUnit · Jest …             (실행 도구 — 다른 층위!)

E2E 두 얼굴  → API E2E(백엔드 끝~끝, UI ✕) vs UI E2E(버튼~화면)
```

## 마무리 — 왜 이 지도가 필요한가

테스트 용어가 무서웠던 건, **서로 다른 자로 잰 것들을 한 줄에 늘어놔서**였다. 축으로 나누면 — 범위(피라미드), 관점(블랙/화이트박스), 계층(컨트롤러/서비스/리포지토리), 그리고 그 위를 도는 실행 도구(JUnit) — 각자 제자리를 찾는다.

여기까지가 테스트의 **지형도**다. 이제 남은 건 이론이 아니라 손이다. 이 지도를 들고, 실제 코드에 `@WebMvcTest` 하나, 서비스 단위 테스트 하나를 직접 짜 보면 — 지도 위의 지명들이 발밑의 길이 된다. 나에게는 이 그림을 그려 본 뒤로 *"이 테스트는 어느 축의 무엇인가"* 를 고를 수 있게 됐고, 그때부터 테스트가 막막함이 아니라 도구가 됐다. 결국 여기서도 방향은 하나였다 — 흩어진 이름들을, 몇 개의 축으로 모아 손에 잡히게.

스프링을 배우다 보면 **캐싱·이벤트 처리·비동기 처리**가 나온다. 이름이 다 그럴듯해서 헷갈리는데, 사실 셋은 **서로 대체하는 게 아니라 목적이 완전히 다른** 도구다. 축을 나누면 명확해진다.

## 한 줄 핵심 — 푸는 문제가 다르다

```
캐싱      → "반복을 줄여 빠르게"   (성능)
이벤트    → "발생을 알려 분리"     (결합도)
비동기    → "기다리지 않고 병렬"   (응답성)
```

목적이 **성능이냐·분리냐·응답성이냐** — 이 셋으로 나뉜다. 하나씩 보자.

## ① 캐싱(Caching) — 반복 조회를 빠르게

자주 쓰는 데이터를 **미리 저장해두고 재사용**하는 것. 목적은 **성능(속도)**이다.

```java
@Cacheable("products")
public Product getProduct(Long id) {
    return productRepository.find(id);   // 이 DB 조회를 두 번째부턴 건너뜀
}
```

```
1번째 호출: DB 조회 → 결과를 캐시에 저장
2번째 호출: DB 안 감! 캐시에서 바로 (빠름)
```

- **푸는 문제**: 같은 데이터를 반복 조회하는 게 느림
- **스프링**: `@Cacheable`, `@CacheEvict`(캐시 비우기), `@EnableCaching`

## ② 이벤트 처리 — 발생을 알려 느슨하게 연결

어떤 일이 **일어났을 때(이벤트) 알림을 보내고, 관심 있는 쪽이 반응**하는 것. 목적은 **결합도 낮추기(분리)**다.

강결합과 비교하면 차이가 보인다.

```java
// ❌ 강결합 — 주문 코드가 이메일·재고를 다 알아야 함
orderService.save(order);
emailService.send(order);      // 직접 호출
stockService.reduce(order);    // 직접 호출

// ✅ 이벤트 — 주문 코드는 "주문됨"만 알림, 나머진 각자 반응
publisher.publishEvent(new OrderCreatedEvent(order));
```

```java
@EventListener
public void sendEmail(OrderCreatedEvent e) { /* 이메일 발송 */ }

@EventListener
public void reduceStock(OrderCreatedEvent e) { /* 재고 차감 */ }
```

주문 코드는 **누가 반응하는지 몰라도 된다.** 이메일·재고 로직이 바뀌거나 새 리스너가 붙어도, 주문 코드는 그대로다.

- **푸는 문제**: 컴포넌트끼리 너무 단단히 묶임(강결합)
- **스프링**: `ApplicationEventPublisher`, `@EventListener`

## ③ 비동기 처리 — 기다리지 않고 딴 스레드로

오래 걸리는 작업을 **별도 스레드에서 실행**하고, 호출자는 **기다리지 않는** 것. 목적은 **응답성**이다.

```java
@Async
public void sendEmail(String to) {
    // 3초 걸리는 이메일 발송
}
```

```
동기:  주문 저장 → 이메일 발송(3초 대기) → 응답   ← 사용자 3초 기다림
비동기: 주문 저장 → 이메일 발송(딴 스레드로) → 즉시 응답  ← 안 기다림
                     (이메일은 뒤에서 알아서 감)
```

- **푸는 문제**: 오래 걸리는 작업 때문에 사용자가 기다림
- **스프링**: `@Async`, `@EnableAsync`, `CompletableFuture`

## 비교표

| | 캐싱 | 이벤트 처리 | 비동기 처리 |
|---|---|---|---|
| **목적** | 성능(속도) | 결합도 분리 | 응답성 |
| **푸는 문제** | 반복 조회 느림 | 컴포넌트 강결합 | 오래 걸리는 작업 대기 |
| **축** | 데이터 재사용 | 통신 방식 | 실행 방식 |
| **스프링** | `@Cacheable` | `@EventListener` | `@Async` |

## 하나의 시나리오로 — 셋이 다 나온다

주문 처리 하나에 셋이 각자 역할을 한다.

```
사용자 주문 요청
 │
 ├─ 상품 정보 조회 ──────────── [캐싱] 캐시에서 빠르게
 ├─ 주문 저장
 ├─ "주문완료" 이벤트 발행 ───── [이벤트] 발행-구독으로 분리
 │     ├─ 이메일 발송 리스너 ── [비동기] @Async로 안 기다림
 │     └─ 재고 차감 리스너
 │
 └─ 사용자에게 즉시 응답
```

- **캐싱**: 상품 정보를 빠르게 (성능)
- **이벤트**: 주문 코드가 이메일·재고를 몰라도 되게 (분리)
- **비동기**: 이메일 발송을 기다리지 않게 (응답성)

셋이 **서로 다른 층에서 협력**하는 것이지, 경쟁하는 게 아니다.

## 이벤트 vs 비동기 — 헷갈리는 지점

이 둘은 자주 **함께** 쓰여서 같은 것처럼 보이지만, 축이 다르다.

```
@EventListener           → 기본은 동기 (발행하면 그 자리에서 리스너 실행)
@Async + @EventListener  → 비동기 (리스너를 딴 스레드에서)
```

- **이벤트** = "누가 반응하나" (**통신 구조**)
- **비동기** = "어느 스레드에서" (**실행 방식**)

그래서 이벤트를 **동기로도, 비동기로도** 처리할 수 있다. 이벤트가 곧 비동기인 게 아니다.

## 정리

```
캐싱    = 반복 조회를 저장해서 빠르게   (성능)   @Cacheable
이벤트  = 발생을 알려 느슨하게 연결     (결합도) @EventListener
비동기  = 기다리지 않고 딴 스레드로     (응답성) @Async
```

- 셋은 **대체 관계가 아니라 다른 문제**를 푼다 — 성능·결합도·응답성
- 종종 **한 흐름에서 함께** 등장한다 (주문 시나리오)
- **이벤트와 비동기는 다른 축** — 통신 구조 vs 실행 방식

세 단어가 무서웠던 건 *"다 성능/처리 관련 같은데 뭐가 다르지"* 싶어서였다. 근데 **"무엇을 위해 쓰나"**로 나누면 — 빠르게(캐싱), 떼어내려고(이벤트), 안 기다리려고(비동기) — 각자 제자리를 찾는다. 이 셋을 실제로 **무엇이 구현하는지**(Redis·Kafka·RabbitMQ)는 [이어지는 글](/blog/caching-event-async-middleware/)에서 본다. 결국 여기서도 방향은 하나였다 — 서로 다른 수고를, 서로 다른 축의 도구로 나눠 던다.

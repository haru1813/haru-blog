[개발환경 세팅 글](/blog/frontend-dev-setup/)에서 *"Vite가 소스코드를 브라우저가 이해하는 JS로 변환·묶어준다"* 고 했다. 그 **"묶어준다"** 가 바로 **번들링**이다. 웹팩·Vite 같은 이름이 계속 나오는데, 이게 뭐고 왜 필요한지, 그리고 React·Vue 공통인지 정리한다.

## 번들(Bundle) — 여러 파일을 하나로

**번들링**은 흩어진 여러 파일(JS·CSS·이미지)을 **하나(또는 몇 개)로 합치는** 것이고, 그 결과물이 **번들**이다.

```
개발할 때 (파일 수십~수백 개)            배포할 때 (번들)
├── App.jsx
├── Header.jsx           ──번들링──▶     bundle.js  (하나로 묶임)
├── ProductCard.jsx
├── utils.js
└── styles.css
```

## 왜 묶나

개발할 땐 파일을 **컴포넌트별로 잘게 쪼개서** 관리한다([컴포넌트 트리](/blog/react-vs-vue/)). 그런데 브라우저가 그 수십 개를 **하나하나 따로 요청**하면 매우 느리다.

```
❌ 안 묶으면: 브라우저가 파일 100개를 100번 요청 (느림)
✅ 묶으면:    번들 몇 개만 요청 (빠름)
```

그래서 배포 전에 **하나로 묶어(번들) 최적화**한다.

## 번들러 — 묶어주는 도구 (웹팩·Vite)

**번들러(bundler)**가 그 번들링을 해주는 도구다. **웹팩(Webpack)**이 대표적이었다. 번들러는 묶는 것 말고도 이런 일을 한다.

```
번들러가 하는 일:
  ① 번들링    — 여러 파일을 하나로 합치기
  ② 트랜스파일 — JSX·TS를 브라우저가 아는 순수 JS로 변환
  ③ 최적화    — 압축(minify), 안 쓰는 코드 제거(트리 셰이킹)
```

- **번들링** — 파일 합치기
- **트랜스파일** — 브라우저는 JSX나 최신 문법을 모르니, 이해 가능한 JS로 번역 (Babel 등)
- **최적화** — 파일 크기를 줄여(minify) 로딩을 빠르게, `import`했지만 안 쓴 코드는 제거(**트리 셰이킹**)

## 웹팩에서 Vite로

웹팩은 오래 표준이었지만 **느렸다**(개발 서버 켤 때 전체를 다 번들해야 시작). 그래서 요즘은 **Vite**로 넘어왔다.

| | 웹팩(Webpack) | Vite |
|---|---|---|
| 시대 | 예전 표준 | **요즘 대세** |
| 개발 속도 | 느림 (전체 번들 후 시작) | **빠름** (필요한 것만 즉시) |
| 쓰인 곳 | CRA·Vue CLI (구형) | 신규 React·Vue |

Vite는 개발 중엔 빠른 도구(esbuild)로 즉시 띄우고, 배포 빌드 때만 번들링(Rollup)한다. [세팅 글](/blog/frontend-dev-setup/)에서 `npm run dev`가 즉시 뜨고 저장하면 바로 반영된 게, Vite가 웹팩처럼 매번 전체를 번들하지 않기 때문이다.

## React·Vue 공통이다

여기가 핵심이다. **번들러는 프레임워크와 무관한 "빌드 도구"** 다.

```
번들러(웹팩·Vite)는 특정 프레임워크 것이 아님
  → React도, Vue도, Angular도 다 씀
```

번들링은 **프론트엔드 공통 단계**라, React 프로젝트든 Vue 프로젝트든 배포하려면 **똑같이 번들러로 묶는다.** [세팅 글](/blog/frontend-dev-setup/)에서 `npm run build`가 React·Vue 둘 다 동일했던 이유가 이거다 — 뒤에서 번들러가 도니까.

## 백엔드로 치면 — 이미 아는 개념이다

사실 하루님은 이걸 백엔드에서 이미 봤다.

```
백엔드: Gradle/Maven이 수많은 .class + 라이브러리 → 하나의 JAR로 패키징
프론트: 번들러(웹팩/Vite)가 수많은 .js/.css → 하나의 번들로

     → 완전히 같은 원리! (여러 조각을 배포용 하나로 묶음)
```

[Maven/Gradle 글](/blog/maven-vs-gradle/)에서 *"여러 클래스와 의존성을 JAR로 묶어 배포"* 라고 했는데, **프론트의 번들러가 정확히 그 역할**이다. 언어만 다르지 개념은 같다.

## 정리

- **번들** = 여러 파일을 묶은 결과(`bundle.js`) / **번들링** = 묶는 과정
- **왜** — 파일이 많으면 브라우저 요청이 폭발 → 묶어서 최적화
- **번들러** = 묶어주는 도구 — **번들링 + 트랜스파일(JSX→JS) + 최적화(압축·트리셰이킹)**
- **웹팩(옛날) → Vite(요즘)** — Vite가 훨씬 빠름
- **React·Vue 공통** — 프레임워크 무관한 빌드 도구
- **비유** — 백엔드의 **Gradle→JAR** 과 같은 원리

번들링이라는 말이 어려워 보였는데, 결국 *"흩어진 파일을 배포용으로 하나로 묶는 것"* 이다. 그리고 그건 백엔드에서 Gradle이 JAR을 만들던 그 일과 똑같다. 나에게는 이 연결(프론트 번들 = 백엔드 JAR)을 잡고 나니, 웹팩·Vite가 더 이상 낯선 프론트 용어가 아니라 *"아, 빌드 도구구나"* 로 익숙해졌다. 결국 여기서도 방향은 하나였다 — 잘게 나눠 개발한 것을, 배포할 땐 효율적으로 하나로 묶는다.

[앞 글](/blog/caching-event-async/)에서 캐싱·이벤트·비동기가 **무엇을** 하는지 봤다. 그런데 실무에서는 Redis·Kafka·RabbitMQ·Elasticsearch 같은 이름이 같이 나온다. 이것들이 바로 그 개념을 **실제로 구현하는 도구(미들웨어)**다. 어느 도구가 어느 개념에 붙는지, 그리고 Elasticsearch만 왜 별개인지 정리한다.

## 개념 vs 도구 — 익숙한 패턴

[JPA 글](/blog/db-access-jdbc-to-jpa/)에서 *"JPA(명세)를 Hibernate(구현)가 실현한다"* 고 했다. 여기도 똑같다.

```
개념(무엇을)          도구(그걸 해주는 미들웨어)
─────────────────────────────────────
캐싱          →      Redis
이벤트 처리    →      Kafka · RabbitMQ (앱 간) / @EventListener (앱 내부)
비동기 처리    →      Kafka · RabbitMQ (앱 간) / @Async (앱 내부)
검색          →      Elasticsearch ← 별개!
```

캐싱이라는 **개념**을 Redis라는 **도구**가 구현하는 것이다. 하나씩 보자.

## ① Redis — 캐싱의 대표 도구

**인메모리 저장소**다. 데이터를 메모리에 두어 **엄청 빠르다.** 앞 글의 `@Cacheable`이 저장하는 곳이 주로 Redis다.

```
@Cacheable ──저장──▶ Redis (메모리) ──▶ 빠른 재조회
```

- **주력: 캐싱** — DB 앞단에서 자주 쓰는 데이터를 캐시
- 다재다능 — **pub/sub(간단한 이벤트)·큐**도 가능, 세션 저장·랭킹·카운터에도 씀

## ② Kafka — 이벤트 스트리밍 + 비동기 (대용량)

**분산 이벤트 스트리밍** 플랫폼이다. 이벤트를 **대용량으로** 발행하고 여러 구독자가 받는다.

```
서비스A ──"주문됨"──▶ Kafka ──▶ 서비스B(이메일)·C(재고)·D(분석)
```

- **이벤트 처리 + 비동기 메시징** 둘 다 (메시징이니까)
- 특징: **엄청난 처리량**, 이벤트를 **로그로 보관**(나중에 재처리 가능), MSA 간 통신, 실시간 스트림 분석

## ③ RabbitMQ — 메시지 큐 + 비동기

전통적인 **메시지 브로커(큐)**다. 작업을 큐에 넣고 컨슈머가 꺼내 처리한다.

```
주문 서비스 ──작업을 큐에──▶ RabbitMQ ──▶ 워커가 꺼내 처리 (비동기)
```

- **비동기 처리 + 서비스 간 메시징**
- 특징: **정교한 라우팅**, 낮은 지연, 전통적 작업 큐에 강함

### Kafka vs RabbitMQ

둘 다 메시징인데 결이 다르다.

| | Kafka | RabbitMQ |
|---|---|---|
| 성격 | **이벤트 스트림** | **작업 큐** |
| 강점 | 대용량·로그 보관·재처리 | 정교한 라우팅·낮은 지연 |
| 비유 | 이벤트의 **강** | 작업의 **우체국** |

*"대용량 이벤트를 흘려보내고 나중에 재처리"* 면 Kafka, *"작업을 정교하게 분배"* 면 RabbitMQ 쪽이다.

## 앱 내부 vs 앱 간(분산) — 중요한 구분

같은 이벤트·비동기라도 **범위**에 따라 도구가 다르다.

```
앱 "안"에서   → @EventListener(이벤트) · @Async(비동기)   ← 스프링 기본
앱 "간"에서   → Kafka · RabbitMQ                        ← 별도 미들웨어 (MSA)
```

한 애플리케이션 안이면 스프링 기본(`@EventListener`·`@Async`)으로 충분하다. **여러 서비스가 통신**해야 하면(MSA) Kafka·RabbitMQ 같은 **메시지 브로커**가 필요하다. 규모가 커질 때 안에서 밖으로 확장되는 것이다.

## Elasticsearch는 왜 별개인가

하루님이 자주 같이 듣는 이름이지만, **Elasticsearch는 캐싱/이벤트/비동기가 아니다.** **검색 엔진**이다.

```
Elasticsearch = 전문 검색(full-text search) + 로그 분석
```

- **검색**: *"제목에 '하루'가 들어간 글 찾기"* 같은 빠른 전문 검색
- **로그 분석**: ELK 스택(Elasticsearch + Logstash + Kibana)으로 로그 수집·시각화

즉 완전히 **다른 축(검색·분석)**이라, 앞의 세 개념과 묶으면 안 된다. (ES 자체는 나중에 검색을 다루는 글에서 따로 파면 좋다.)

## 매핑표 (전체)

| 도구 | 정체 | 관련 개념 |
|---|---|---|
| **Redis** | 인메모리 저장소 | 캐싱 (주력) + pub/sub·큐 |
| **Kafka** | 분산 이벤트 스트리밍 | 이벤트 + 비동기 (대용량) |
| **RabbitMQ** | 메시지 브로커(큐) | 비동기 + 메시징 |
| **Elasticsearch** | 검색 엔진 | ✗ 검색·분석 (별개) |

## 정리

- 캐싱·이벤트·비동기는 **개념(무엇을)**, 이 미들웨어는 **구현(어떻게)** — [JPA-Hibernate](/blog/db-access-jdbc-to-jpa/)와 같은 명세/구현 관계
- **Redis** = 캐싱 (+pub/sub·큐) / **Kafka** = 이벤트+비동기(대용량) / **RabbitMQ** = 비동기+큐
- **Kafka(이벤트 스트림)** vs **RabbitMQ(작업 큐)** — 결이 다름
- **앱 내부**(`@EventListener`·`@Async`) vs **앱 간**(Kafka·RabbitMQ, MSA)
- **Elasticsearch는 검색 엔진** — 세 개념과 무관, 별개 축

지금 단계에선 다 쓸 일이 없다 — 규모가 커지고(MSA·대용량) 필요가 생겨야 하나씩 도입한다. 그러니 지금은 *"캐싱은 Redis, 메시징은 Kafka/RabbitMQ, 검색은 Elasticsearch"* 라는 **지도만 손에 쥐면** 충분하다. 나에게는 이 이름들이 무섭게 들렸던 게, "개념을 구현하는 도구"라는 걸 알고 나니 제자리를 찾았다. 결국 여기서도 방향은 하나였다 — 개념을 먼저 잡고, 그걸 실현하는 도구는 필요할 때 골라 얹는다.

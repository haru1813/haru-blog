[서블릿 글](/blog/servlet-dynamic-web-project/)에서 "서블릿은 요청을 받아 응답한다"고 했다. 그런데 여기엔 한 가지 불편한 진실이 있다. **HTTP는 방금 누가 다녀갔는지 기억하지 못한다.** 요청 하나가 끝나면 연결도 끝나고, 서버는 다음 요청이 "아까 그 사람"인지 알 방법이 없다. 이걸 **stateless(무상태)**라고 한다.

로그인을 생각해 보자. 로그인 요청과 그다음 "내 정보 보기" 요청은 서버 입장에서 **완전히 남남**이다. 그럼 어떻게 "로그인한 사용자"를 계속 알아볼까? 그 답이 **쿠키와 세션**이다.

## 쿠키 — 손님 손에 쥐여 주는 표

쿠키(Cookie)는 **브라우저(클라이언트)에 저장되는 작은 데이터**다. 서버가 응답할 때 "이거 갖고 있어" 하고 쿠키를 내려 주면, 브라우저는 그걸 저장했다가 **다음 요청부터 자동으로 함께 보낸다.**

- 저장 위치: **클라이언트(브라우저)**
- 형태: `이름=값` (예: `theme=dark`)
- 특징: 요청마다 자동 전송, 만료 시간·도메인·경로 지정 가능

즉 서버가 손님 손에 **번호표**를 쥐여 주고, 손님은 올 때마다 그 표를 내미는 식이다.

```java
Cookie cookie = new Cookie("theme", "dark");
cookie.setMaxAge(60 * 60 * 24 * 7); // 7일간 유지(초 단위)
cookie.setHttpOnly(true);           // JS로 접근 못 하게(보안)
resp.addCookie(cookie);
```

## 세션 — 표 번호만 주고, 정보는 서버가 보관

쿠키에 사용자 정보를 통째로 담으면? 브라우저에 다 노출되니 위험하다. 그래서 나온 게 세션이다.

세션(Session)은 **정보를 서버에 저장**하고, 클라이언트에는 그 정보를 찾을 **열쇠(세션 ID)만** 쿠키로 준다.

- 저장 위치: **서버**
- 클라이언트에는: **세션 ID**만 쿠키로 전달 (보통 `JSESSIONID`)
- 서버는 그 ID로 "이 사람이 누구인지"를 찾아낸다

식당 비유로 — 손님에게는 **보관표 번호(세션 ID)**만 주고, 실제 코트(사용자 정보)는 **카운터(서버)**가 보관하는 것이다. 번호표만으로는 남이 뭘 맡겼는지 알 수 없다.

```java
// 로그인 성공 시
HttpSession session = req.getSession();
session.setAttribute("userId", "haru");

// 이후 요청에서 사용자 확인
String userId = (String) session.getAttribute("userId");

// 로그아웃
session.invalidate();
```

## 한눈에 보는 차이

| | 쿠키 | 세션 |
|---|---|---|
| 저장 위치 | 클라이언트(브라우저) | 서버 |
| 담기는 것 | 값 자체 | 서버엔 정보, 클라엔 ID만 |
| 보안 | 상대적으로 취약(노출됨) | 상대적으로 안전 |
| 용량 | 작음(4KB 정도) | 서버 용량만큼 |
| 서버 부담 | 없음 | 있음(세션 저장) |

## 로그인은 이렇게 흐른다

```
1. 로그인 요청  ── id/pw ──▶  서버
2. 서버: 인증 성공 → 세션 생성(정보 저장)
3. 서버 → 브라우저 : 세션 ID를 쿠키로 전달 (JSESSIONID)
4. 이후 모든 요청 : 브라우저가 그 쿠키를 자동 전송
5. 서버 : 세션 ID로 "아, 하루구나" 하고 식별
```

핵심은 **세션도 결국 쿠키를 타고 다닌다**는 점이다. 세션 ID를 실어 나르는 수단이 쿠키다. 둘은 경쟁 관계가 아니라 **협력 관계**다.

## 보안 — 번호표를 훔치면 어떻게 될까

세션 ID가 든 쿠키를 누가 가로채면, 그 사람이 나인 척할 수 있다. 이걸 **세션 하이재킹**이라 한다. 그래서 최소한 이 정도는 챙긴다.

- **`HttpOnly`**: JavaScript로 쿠키에 접근하지 못하게 → XSS로 세션 ID 탈취 방지
- **`Secure`**: HTTPS 연결에서만 쿠키 전송 → 중간에서 훔쳐보기 방지
- **로그인 후 세션 ID 재발급**: 세션 고정(Session Fixation) 공격 방지

## PHP를 하다 Java로 오니

이 개념은 언어를 옮겨도 **뼈대가 똑같았다.**

- **PHP**에서는 `session_start()` 후 `$_SESSION['userId']`에 담았다. 서버 어딘가(기본은 파일)에 저장되고, 브라우저엔 `PHPSESSID` 쿠키가 오갔다.
- **Java/서블릿**에서는 `request.getSession()` 후 `setAttribute()`. 브라우저엔 `JSESSIONID`가 오간다.

이름만 `PHPSESSID` → `JSESSIONID`로 바뀌었을 뿐, **"정보는 서버에, ID는 쿠키로"**라는 원리는 완전히 같았다. 뿌리를 알면 언어는 방언 차이일 뿐이다.

## Spring, 그리고 요즘

Spring에서도 `HttpSession`을 그대로 쓸 수 있다. 다만 요즘은 서버가 여러 대로 늘어나면서(세션을 어느 서버가 가졌는지 문제가 생긴다) **세션 대신 토큰(JWT)** 으로 상태를 클라이언트가 들고 다니게 하는 방식도 많이 쓴다. 그건 다음에 따로 정리할 생각이다.

## 정리

- **HTTP는 stateless** — 이전 요청을 기억하지 못한다.
- **쿠키**: 클라이언트에 저장, 요청마다 자동 전송. (번호표)
- **세션**: 정보는 서버에, ID만 쿠키로. 더 안전하다. (보관표)
- **둘은 협력**: 세션 ID가 쿠키를 타고 다닌다.
- **보안**: `HttpOnly`·`Secure`·세션 ID 재발급으로 하이재킹을 막는다.

로그인이 "당연히 되는 것"처럼 보이지만, 그 뒤엔 이렇게 **기억 못 하는 HTTP에 기억을 붙이는** 장치가 돌아가고 있다.

지금까지 이 블로그에서 정리한 건 **모놀리식 백엔드**였다. 요청 흐름·데이터·보안·테스트·캐싱까지, **하나의 애플리케이션** 안에서 벌어지는 일들. 그런데 실무에서는 **MSA(마이크로서비스 아키텍처)**라는 말이 늘 따라붙는다. 이 둘의 차이를 짚으며, 지금까지 배운 것이 **큰 그림 어디에 서 있는지**로 마무리한다.

## 모놀리식 — 하나에 전부

**모놀리식(Monolithic)**은 모든 기능이 **하나의 애플리케이션·하나의 배포 단위**에 담긴 구조다. 주문·회원·결제가 다 한 코드베이스, 한 프로세스 안에 있다.

```
┌─────────────────────────┐
│      하나의 애플리케이션      │
│  회원 · 주문 · 결제 · 배송   │  ← 다 같이, 한 번에 배포
│         ↓                │
│      하나의 DB            │
└─────────────────────────┘
```

- **장점** — **단순하다.** 개발·배포·테스트가 쉽고, 기능 간 호출이 그냥 메서드 호출이라 빠르다. **트랜잭션도 간단**하다([`@Transactional`](/blog/transactional-spring/) 하나로 묶으면 끝)
- **단점** — 커지면 **거대해진다.** 작은 수정에도 **전체를 다시 배포**하고, 한 부분의 장애가 **전체로 번지며**, 특정 기능만 확장하고 싶어도 **전체를 통째로** 늘려야 한다

## MSA — 작은 서비스로 쪼개기

**MSA**는 기능별로 **독립된 작은 서비스**로 나눈다. 회원 서비스, 주문 서비스, 결제 서비스가 각자 **따로 배포·확장·개발**된다.

```
[회원 서비스]  [주문 서비스]  [결제 서비스]   ← 각자 독립 배포
    ↓             ↓             ↓
 회원 DB       주문 DB        결제 DB        ← DB도 따로
    └──────── 네트워크로 통신 ────────┘
```

- **장점** — **독립 배포·확장**(주문만 트래픽 몰리면 주문 서비스만 늘림), **기술 자유**(서비스별 다른 언어·DB), **장애 격리**(결제가 죽어도 회원은 살아있음), 팀별 병렬 개발
- **단점** — **분산의 복잡도.** 서비스 간 **네트워크 통신**(느리고 실패 가능), **데이터 일관성**(DB가 나뉘어 트랜잭션을 한 번에 못 묶음 → 분산 트랜잭션·사가 패턴), **운영·디버깅 부담**(문제가 어느 서비스에서 터졌는지 추적이 어려움)

## 비교표

| | 모놀리식 | MSA |
|---|---|---|
| 구조 | 하나의 앱 | 여러 독립 서비스 |
| 배포 | 통째로 한 번에 | 서비스별 따로 |
| 확장 | 전체를 늘림 | 필요한 서비스만 |
| 통신 | 메서드 호출 (빠름) | 네트워크 (느림·실패 가능) |
| 트랜잭션 | 간단 (`@Transactional`) | 어려움 (분산 트랜잭션) |
| 장애 | 전체로 번짐 | 서비스별 격리 |
| 복잡도 | **낮음** | **높음** |
| 시작 | 쉬움 | 인프라 부담 큼 |

## 지금까지 배운 것이 MSA에서 쓰인다

여기가 이 글의 핵심이다. 그동안 배운 개념 중 몇 개는 사실 **"모놀리식만으론 안 되고, 분산되면 필요해지는 것"** 이었다. 이제 그 이유가 이어진다.

| 배운 것 | MSA에서의 자리 |
|---|---|
| **[메시징](/blog/messaging-spring/)** (Kafka·RabbitMQ) | 서비스 **간 비동기 통신** (다른 서버에 알림) |
| **[JWT](/blog/spring-security-jwt/)** (stateless) | 서버가 여러 개라 **세션 공유 없이** 인증 |
| **[Redis 분산 세션](/blog/spring-security-session/)** | 굳이 세션 쓸 때 **여러 서버가 공유** |
| **[traceId·MDC](/blog/logging/)** | 요청이 여러 서비스를 거쳐도 **하나로 추적** |
| **[캐싱(Redis)](/blog/caching-event-async-middleware/)** | 서비스들이 **공유하는 캐시** |

*"세션 대신 왜 JWT?"*, *"왜 메시지 큐?"*, *"traceId는 왜?"* — 그 답이 전부 **"서버가 여러 대로 나뉘니까"** 였다. 즉 하루님은 모놀리식을 배우면서, 이미 **MSA로 가는 다리**들을 하나씩 건너온 것이다.

## 그런데 — 대부분 "모놀리식 먼저"다

MSA가 멋져 보여도, 유명한 조언이 있다 — **"Monolith First"**(모놀리식 먼저). 이유는 명확하다.

```
성급한 MSA → 분산 복잡도(네트워크·데이터 일관성·운영)를 감당 못 해 오히려 독
현명한 순서 → 모놀리식으로 잘 만들고, 정말 커지면 그때 쪼갠다
```

- **작은 서비스·초기 스타트업** → 모놀리식이 압도적으로 유리 (빠르고 단순)
- **규모·트래픽·팀이 커져서** 모놀리식이 한계에 부딪힐 때 → MSA로 전환

즉 **모놀리식을 잘 아는 것이 먼저**다. MSA는 모놀리식을 쪼갠 것이라, 모놀리식 안에서 계층을 잘 나누고(컨트롤러·서비스·리포지토리) 결합도를 낮춘([이벤트](/blog/event-handling-spring/)·[DI](/blog/dependency-injection-methods/)) 사람이, 나중에 서비스로도 잘 쪼갠다. 하루님이 지금까지 다진 게 **바로 그 기본기**다.

## 정리

- **모놀리식** = 하나의 앱에 전부 (단순·빠름, 커지면 무거움)
- **MSA** = 작은 서비스로 분리 (독립 배포·확장·장애격리, 분산 복잡도)
- 그동안 배운 **메시징·JWT·traceId·분산 캐시**가 다 **"분산되면 필요한 것"** 이었다
- **대부분 모놀리식 먼저** — 잘 만든 모놀리식이 MSA의 출발점

이 블로그의 개념 여정은 여기서 매듭짓는다. 되짚어보면 — 요청 하나가 컨트롤러까지 오는 길부터, 데이터가 DTO로 변신하고, 트랜잭션으로 묶이고, 시큐리티로 지켜지고, 테스트로 검증되고, 캐시·이벤트·메시지로 흐르는 것까지. **하나의 모놀리식 백엔드가 어떻게 살아 움직이는지**를 처음부터 끝까지 그려낸 셈이다.

그리고 이제, 지도는 충분하다. 다음은 **실습**이다 — 이 개념들을 손으로 짜보며, 지도 위의 지명들을 발밑의 길로 바꿀 차례다. `@WebMvcTest` 하나, JPA 연관관계 하나, JWT 필터 하나를 직접 만들다 막히는 그 순간이, 사실 가장 많이 배우는 순간이니까. 결국 여기서도 방향은 하나였다 — 읽어서 세운 뼈대에, 짜면서 살을 붙인다.

Spring 프로젝트를 처음 만들면, 코드를 한 줄 쓰기도 전에 갈림길이 나온다 — **Maven이냐 Gradle이냐.** [Spring Initializr](https://start.spring.io)에서도 제일 먼저 이걸 고르라고 한다. 둘 다 "빌드 도구"라는데, 애초에 빌드 도구가 왜 필요하고, 이 둘은 뭐가 다른 걸까.

## 먼저, 빌드 도구가 왜 필요한가

자바 프로젝트 하나를 돌리려면 남이 만든 라이브러리(JAR)가 잔뜩 필요하다. Spring, JDBC 드라이버, 로깅, 테스트 도구… 이걸 **일일이 사이트에서 내려받아 폴더에 넣고, 버전 올라갈 때마다 다시 받는다**고 생각해 보라. 지옥이다. 게다가 라이브러리가 또 다른 라이브러리를 필요로 하는(의존성의 의존성) 경우까지 손으로 챙겨야 한다.

빌드 도구는 이 두 가지를 대신해 준다.

- **의존성 관리** — *"이 라이브러리 이 버전 필요해"*라고 적기만 하면, 저장소에서 알아서 내려받고 딸린 것까지 챙긴다.
- **빌드 자동화** — 컴파일 → 테스트 → 패키징(JAR/WAR) → 배포까지의 과정을 명령 한 줄로 돌린다.

PHP를 해 봤다면 **Composer**를, Node를 해 봤다면 **npm**을 떠올리면 된다. 자바 진영에서 그 역할을 하는 대표 주자가 Maven과 Gradle이다.

## 빌드 도구와 패키지 매니저, 같은 걸까

방금 Composer·npm에 빗댔지만, 엄밀히 따지면 이 둘과 Maven·Gradle은 **결이 조금 다르다.** 헷갈리기 쉬운 지점이라 짚고 넘어간다.

- **패키지 매니저** — 외부 라이브러리를 내려받고 버전을 맞추는 **의존성 관리 전담**. PHP의 `Composer`, Python의 `pip`가 대표적이다.
- **빌드 도구** — 의존성 관리에 더해 **컴파일 → 테스트 → 패키징(JAR/WAR) → 배포**까지, 빌드 생명주기 전체를 돌린다.

즉 **빌드 도구가 패키지 매니저 기능을 품고 있는** 구조다. Maven·Gradle은 "패키지 매니저"가 아니라 *"패키지 매니저 역할까지 내장한 빌드 도구"*인 셈이다. 그래서 자바에는 Composer 같은 **별도 패키지 매니저가 따로 없다** — Maven·Gradle이 그 일까지 겸한다.

| 언어 | 패키지 매니저 | 빌드 도구 |
|---|---|---|
| PHP | Composer | (거의 불필요) |
| JavaScript | npm · yarn | Vite · webpack 등 |
| Python | pip | (poetry 등) |
| **Java** | — (별도 없음) | **Maven · Gradle** (의존성까지 겸함) |

왜 자바만 이렇게 합쳐졌을까? **컴파일 언어라서 그렇다.** PHP는 소스를 그대로 실행하는 인터프리터 언어라 "빌드"라 부를 단계가 거의 없다. 그래서 의존성만 챙기는 Composer로 충분하다. 반면 자바는 **소스(`.java`) → 바이트코드(`.class`) → 패키징(`.jar`)** 이라는 빌드 과정이 반드시 필요하고, 이왕 빌드를 관리할 도구가 있으니 의존성 관리까지 그 안으로 흡수된 것이다.

> PHP에서 `composer install`만 하던 사람이, 자바에서 `mvn package` 한 줄에 컴파일·테스트·JAR 생성이 우르르 일어나는 걸 보고 놀라는 이유가 여기 있다. Composer가 "라이브러리 담당"이라면, Maven·Gradle은 "라이브러리 **+** 빌드 담당"이다.

## Maven — XML로 규약을 따르는 전통의 강자

Maven은 설정을 **`pom.xml`**이라는 XML 파일에 적는다. 의존성 하나를 추가하면 이렇게 생겼다.

```xml
<!-- pom.xml -->
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <version>3.2.0</version>
  </dependency>
</dependencies>
```

Maven의 핵심 철학은 **"규약이 설정보다 우선(Convention over Configuration)"**이다. 소스는 `src/main/java`, 테스트는 `src/test/java`, 빌드 결과는 `target/` — 이런 위치를 **정해진 관례로 고정**해 둔다. 그래서 어느 Maven 프로젝트를 열어도 구조가 똑같고, 처음 보는 사람도 길을 잃지 않는다.

빌드는 정해진 **라이프사이클**을 따른다. `compile → test → package → install → deploy` 순서가 못 박혀 있고, 명령도 그대로다.

```bash
mvn package   # 컴파일·테스트·JAR 패키징까지
```

장점은 **예측 가능성과 안정성**이다. XML이라 장황하지만, 그만큼 정형적이고 누가 봐도 구조가 명확하다. 오래된 만큼 자료와 레퍼런스도 압도적으로 많다. 대신 XML은 **조건 분기나 커스텀 로직을 넣기가 답답**하다. 정해진 틀 안에서는 편하지만, 틀을 벗어나려는 순간 벽에 부딪힌다.

## Gradle — 코드로 유연하게, 그리고 빠르게

Gradle은 설정을 XML이 아니라 **스크립트(DSL)**로 적는다. Groovy(`build.gradle`) 또는 Kotlin(`build.gradle.kts`)을 쓴다. 같은 의존성을 이렇게 적는다.

```groovy
// build.gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web:3.2.0'
}
```

XML 예닐곱 줄이 한 줄로 줄었다. **설정이 곧 코드**라서, `if` 분기를 넣든 반복문을 돌리든 자유롭다. Maven이 "정해진 틀"이라면 Gradle은 "내가 짜는 틀"이다.

그리고 Gradle의 진짜 무기는 **속도**다.

- **증분 빌드(Incremental Build)** — 바뀐 부분만 다시 빌드한다. 안 바뀐 건 건너뛴다.
- **빌드 캐시(Build Cache)** — 한 번 만든 결과를 재사용한다.
- **데몬(Daemon)** — 백그라운드에 상주하며 매번 새로 뜨는 비용을 없앤다.

Maven이 매번 전체를 처음부터 도는 것과 달리, Gradle은 이 세 가지로 **반복 빌드를 훨씬 빠르게** 만든다. 프로젝트가 커질수록 이 차이는 크게 벌어진다. 안드로이드가 공식 빌드 도구로 Gradle을 택한 것도 이 때문이다.

대신 **유연한 만큼 학습 곡선이 있다.** DSL 문법을 익혀야 하고, 자유도가 높은 만큼 프로젝트마다 빌드 스크립트가 제각각이라 남의 설정을 읽기가 Maven보다 어려울 수 있다.

## 한눈에 비교

| 항목 | Maven | Gradle |
|---|---|---|
| 설정 파일 | `pom.xml` (XML) | `build.gradle(.kts)` (Groovy/Kotlin) |
| 성격 | 규약 기반, 정형적 | 스크립트 기반, 유연 |
| 성능 | 매번 전체 빌드 | 증분·캐시·데몬으로 빠름 |
| 가독성 | 장황하지만 구조 명확 | 간결하지만 프로젝트마다 다름 |
| 학습 곡선 | 낮음(정해진 틀) | 있음(DSL 학습) |
| 강점 | 안정성·레퍼런스 풍부 | 속도·확장성 |

## 그래서 뭘 쓸까

Spring Boot는 **둘 다 완벽하게 지원**하므로, 어느 쪽을 골라도 개발 자체엔 지장이 없다. 다만 흐름은 이렇다.

- **새 프로젝트라면 Gradle(특히 Kotlin DSL)이 요즘 추세**다. Spring Initializr의 기본값도 Gradle 쪽으로 기울었고, 빌드 속도와 간결함 때문에 신규 프로젝트가 점점 넘어간다.
- **레거시·대규모 엔터프라이즈에서는 Maven이 여전히 강세**다. 안정성과 예측 가능성, 방대한 사내 자료 때문에 쉽게 바꾸지 않는다. 기존 프로젝트를 유지보수한다면 Maven을 만날 확률이 높다.

여기서도 익숙한 구도가 보인다 — **정해진 규약으로 안정성을 주는 전통(Maven)과, 유연함과 속도로 앞서가는 현대(Gradle).** Spring MVC에서 Spring Boot로 넘어온 그 흐름과 결이 같다. 결국 "반복되는 수고를 덜고, 필요한 만큼 자동으로"라는 방향은 빌드 도구에서도 똑같이 흐르고 있었다.

## 정리

- **빌드 도구 vs 패키지 매니저**: 패키지 매니저(Composer·pip)는 의존성 관리 전담, 빌드 도구(Maven·Gradle)는 거기에 컴파일·테스트·패키징까지 겸한다. 자바는 컴파일 언어라 빌드 도구가 의존성 관리까지 흡수했다.
- **Maven**: `pom.xml`(XML), 규약 기반, 안정적·정형적, 레퍼런스 풍부. 대신 장황하고 유연성이 낮다.
- **Gradle**: `build.gradle`(DSL), 코드로 유연하게, 증분·캐시·데몬으로 빠르다. 대신 학습 곡선이 있다.
- **선택**: 새 프로젝트는 Gradle 추세, 레거시·엔터프라이즈는 Maven 강세. Spring Boot는 둘 다 지원한다.

`pom.xml`이든 `build.gradle`이든, 결국 하는 일은 같다 — *"이 라이브러리 필요해, 이렇게 빌드해 줘"*를 대신 처리해 주는 것. 도구가 달라도 덜어 주려는 수고는 하나다.

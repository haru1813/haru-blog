React와 Vue를 배우려는데, 그 전에 궁금해진다. **"이것들은 대체 왜 나왔을까?"** 답은 **SPA**라는 흐름에 있다. 그리고 SPA의 한계에서 다시 **SSR**과 Next.js·Nuxt.js가 나왔다. 이 흐름을 알면 React·Vue가 *"멋져서"* 가 아니라 *"필요해서"* 나온 것임이 보인다. 백엔드에서 [모놀리식→MSA](/blog/monolithic-vs-msa/)를 짚었듯, 프론트엔드도 흐름부터 잡자.

## 시작 — 전통적 MPA

옛날 웹은 **MPA(Multi Page Application)**였다. [WAS 글](/blog/web-server-vs-was/)에서 본 것처럼, **서버가 매 요청마다 HTML을 완성해서** 통째로 내려줬다.

```
페이지 이동
   ▼
서버가 새 HTML 완성 → 브라우저가 통째로 새로 그림 (하얗게 깜빡)
```

- **장점** — 단순하고, 서버가 완성된 HTML을 주니 검색엔진(SEO)도 잘 읽는다
- **단점** — 페이지를 옮길 때마다 **전체를 새로 받아** 하얗게 깜빡이고, 앱 같은 부드러운 경험이 안 된다

## SPA — 한 페이지에서 다 한다

**SPA(Single Page Application)**는 발상을 뒤집는다. **처음에 페이지를 한 번만 받고**, 이후엔 **자바스크립트가 화면을 갈아끼운다.** 서버에 매번 HTML을 요청하지 않는다.

```
첫 로드: HTML + JS 한 번 받음
   ▼
이후 화면 전환: JS가 필요한 부분만 다시 그림 (새로고침 없음!)
   → 데이터만 API로 받아옴 (JSON)
```

페이지 이동이 **깜빡임 없이 부드럽다.** 웹인데 앱처럼 느껴진다. Gmail·노션 같은 게 다 SPA다.

## 그런데 SPA를 순수 JS로 만들면 지옥이다

SPA는 좋은데, **순수 자바스크립트로 만들려면** 화면을 직접 그리고 지우고, 상태가 바뀔 때마다 어느 DOM을 갱신할지 일일이 관리해야 한다. 앱이 커지면 이게 감당이 안 된다.

**그래서 나온 게 React와 Vue다.** 이들은 SPA를 **편하게** 만들어준다:

- **컴포넌트** — UI를 재사용 가능한 조각으로
- **상태(state)** — 데이터가 바뀌면 **화면을 알아서 갱신**
- **가상 DOM** — 무엇이 바뀌었는지 효율적으로 계산해 최소한만 다시 그림

즉 **React·Vue는 "SPA를 편하게 만들려고" 태어났다.** 순수 JS의 그 고통을 덜어주는 도구다.

## SPA의 두 가지 한계

SPA도 완벽하진 않다. 발목을 잡는 게 둘 있다.

**① 초기 로딩이 느리다**
```
SPA 첫 접속 → JS 뭉치를 다 받아야 → 그제서야 화면이 그려짐
             (그 전엔 빈 화면)
```
첫 화면이 뜨기까지 JS를 다 내려받아 실행해야 해서, 초기 로딩이 느리다.

**② SEO(검색엔진 최적화)에 약하다**
검색엔진 크롤러가 SPA에 오면 **거의 빈 HTML**(`<div id="root"></div>`)만 본다. 내용은 JS가 나중에 채우는데, 크롤러가 그걸 못 읽으면 검색 노출이 안 된다.

## SSR의 귀환 — 그리고 Next·Nuxt

이 한계를 풀려고, **서버에서 미리 렌더링**하는 **SSR(Server Side Rendering)**이 돌아온다. MPA처럼 서버가 HTML을 그려주되, 이후엔 SPA처럼 동작하는 **하이브리드**다.

```
SSR: 서버가 완성된 HTML을 먼저 줌 (빠른 첫 화면 + SEO)
     → 이후엔 JS가 붙어(hydration) SPA처럼 부드럽게
```

그런데 React·Vue **자체엔 SSR·라우팅·빌드 최적화가 없다.** 이걸 다 얹어주는 **"메타 프레임워크"**가 나온다.

| 베이스 | 메타 프레임워크 | 하는 일 |
|---|---|---|
| **React** | **Next.js** | SSR·SSG·라우팅·최적화를 React 위에 |
| **Vue** | **Nuxt.js** | 같은 것을 Vue 위에 |

- **Next.js** = React + (SSR·파일기반 라우팅·이미지 최적화·API 라우트…)
- **Nuxt.js** = Vue + (같은 것들)

즉 Next·Nuxt는 **"React·Vue만으론 부족한 SSR·라우팅 등을 채우려고"** 태어났다. React/Vue가 SPA의 고통을 덜었듯, Next/Nuxt는 SPA의 한계(로딩·SEO)를 던다.

## 전체 흐름 한눈에

```
MPA (서버가 매번 HTML)
   ↓  "페이지 깜빡임이 싫다, 앱처럼 부드럽게"
SPA (JS가 화면 전환)  ← React · Vue 등장 (SPA를 편하게)
   ↓  "초기 로딩 느리고 SEO 약하다"
SSR/메타 프레임워크  ← Next.js · Nuxt.js 등장 (한계 보완)
```

각 단계가 **앞 단계의 불편을 풀며** 나왔다. 이게 프론트엔드의 큰 줄기다.

## 정리

- **MPA** — 서버가 매 요청 HTML 완성 (단순·SEO 좋음, 깜빡임)
- **SPA** — 첫 로드 후 JS가 화면 전환 (부드러움) → 순수 JS론 힘드니 **React·Vue** 등장
- **SPA 한계** — 초기 로딩 느림 + SEO 약함
- **SSR + 메타 프레임워크** — 서버 렌더로 한계 보완 → **Next.js**(React)·**Nuxt.js**(Vue)
- 흐름: **MPA → SPA(React·Vue) → SSR(Next·Nuxt)**

React·Vue가 무엇인지 알기 전에 *"왜 나왔나"* 를 알면, 배우는 게 훨씬 단단해진다 — 이건 순수 JS로 SPA를 만드는 고통을 던 도구고, Next·Nuxt는 그 SPA의 한계를 던 도구다. 이 배경 위에서 [React와 Vue가 구체적으로 무엇이 다른지](/blog/react-vs-vue/), 그리고 [개발환경을 어떻게 세팅하는지](/blog/frontend-dev-setup/)를 이어서 본다. 결국 여기서도 방향은 하나였다 — 앞 세대의 불편을, 다음 도구가 하나씩 덜어낸다.

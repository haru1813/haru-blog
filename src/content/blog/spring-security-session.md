[시큐리티 큰 그림](/blog/spring-security-overview/)에서 인증 상태를 유지하는 방식이 두 갈래라 했다. 그중 전통적인 쪽 — **세션 기반**을 본다. 핵심은 하나다: **서버가 로그인 상태를 "기억"한다.**

## 로그인 흐름 — 세션에 저장

세션 방식에서 로그인이 되면 이런 일이 벌어진다.

```
① 사용자가 아이디·비번으로 로그인
        ▼
② 서버가 검증 (UsernamePasswordAuthenticationFilter)
        ▼
③ 성공 → Authentication을 SecurityContext에 담아
   HttpSession에 저장 (서버 메모리에 보관)
        ▼
④ 서버가 JSESSIONID 쿠키를 응답에 실어 보냄
        ▼
⑤ 브라우저가 그 쿠키를 저장
```

핵심은 **③**이다. 서버가 *"이 세션은 하루가 로그인함"* 을 **자기 메모리(세션)에 기억**한다. 그리고 그 세션을 가리키는 열쇠가 **JSESSIONID**라는 쿠키다. ([쿠키·세션 글](/blog/cookie-session/)의 그 세션이다.)

## 이후 요청 — 쿠키로 상태 복원

한 번 로그인하면, 다음 요청부터는 브라우저가 **JSESSIONID 쿠키를 자동으로** 실어 보낸다.

```
요청 (Cookie: JSESSIONID=abc123)
   ▼
서버: "abc123 세션 찾아보니 → 하루가 로그인한 상태네"
   ▼
SecurityContext 복원 → 로그인된 것으로 처리
```

즉 매 요청마다 다시 로그인할 필요 없이, **쿠키 하나로 서버가 "아 아까 그 사람"** 하고 알아본다. 상태를 **서버가 들고 있는** 것이다.

## stateful — 서버가 기억한다는 뜻

이 방식을 **stateful(상태 있음)** 이라 한다. 서버가 **각 사용자의 로그인 상태를 세션으로 보관**하기 때문이다.

```
서버 메모리
  ├ 세션 abc123 → 하루 (USER)
  ├ 세션 def456 → 민수 (ADMIN)
  └ 세션 ...
```

- **장점** — 서버가 상태를 쥐고 있어서, **로그아웃·강제 만료를 즉시** 할 수 있다 (세션을 지우면 끝). 쿠키엔 열쇠(JSESSIONID)만 있어 가볍다
- **단점** — 사용자가 늘수록 **서버 메모리에 세션이 쌓인다**. 그리고 다음 문제가 진짜 골칫거리다

## 서버가 여러 대면 — 세션 공유 문제

트래픽이 커지면 서버를 **여러 대**로 늘린다(스케일 아웃). 그런데 세션은 **각 서버의 메모리**에 있다. 문제가 생긴다.

```
로그인 요청 → 서버A (세션을 A 메모리에 저장)
다음 요청   → 서버B (로드밸런서가 B로 보냄)
             → 서버B: "이 세션 나한텐 없는데?" → 로그인 풀림! 😱
```

서버A에 저장된 세션을 서버B는 모른다. 그래서 세션 방식은 **서버 확장이 까다롭다.** 해결책이 있긴 하다.

| 해결책 | 방법 |
|---|---|
| **Sticky Session** | 같은 사용자는 늘 같은 서버로 (로드밸런서 고정) |
| **세션 클러스터링** | 서버끼리 세션 복제 (동기화 비용) |
| **[Redis](/blog/caching-event-async-middleware/) 세션 저장** | 세션을 외부(Redis)에 몰아 모든 서버가 공유 ← 실무 주력 |

특히 **Redis에 세션을 저장**(`spring-session-data-redis`)하면, 모든 서버가 같은 곳을 보니 확장 문제가 풀린다. 세션의 장점(즉시 만료)은 살리면서 확장 문제만 해결하는 방식이다.

## 정리

- **로그인** → 서버가 인증 정보를 **세션(메모리)에 저장** + **JSESSIONID 쿠키** 발급
- **이후 요청** → 쿠키로 세션을 찾아 로그인 상태 **복원**
- **stateful** — 서버가 상태를 기억 → **즉시 로그아웃·만료 가능**(장점), **메모리 부담**(단점)
- **확장 문제** — 서버 여러 대면 세션 공유 필요 → Sticky Session / 클러스터링 / **Redis 세션**(주력)

세션 방식은 *"서버가 기억한다"* 는 단순함이 장점이자 한계다. 서버가 하나면 완벽하지만, 여러 대로 늘어나는 순간 *"내 세션이 저 서버엔 없다"* 는 문제가 터진다. 이 **stateful의 한계**를 정반대로 뒤집은 게 [JWT 기반 인증](/blog/spring-security-jwt/) — *"서버는 아무것도 기억하지 말자"* 는 발상이다. 다음 글에서 이어진다.
